How bys sync works

Sync copies your YouTube subscriptions into a local database, describes each channel in plain text, and turns that text into a vector so search can compare it with your query.

Runs

~520

API units for 500 subscriptions, out of 10,000 per day

Stores

3 tables

channels, videos, embeddings in one SQLite file

Embeds

384 numbers

per channel, from a small local model. Nothing is sent to an AI service.

Fails

per channel

one broken channel is logged and skipped, the rest still sync

There are two layers. The network layer asks YouTube what you subscribe to and what each channel uploaded. The local layer stores that data, turns it into text, and embeds the text. Sync touches the network first, then does all the rest on your machine.

YouTube API SQLite Profile text Embedding model

1. Ask YouTube

Steps 1, 2, 3 and 5. Read-only calls to the YouTube Data API.

2. Store

Steps 4, 6, 8 and 10. Writes and reads in the local SQLite file.

3. Describe

Step 7. Combine the channel's name, description and recent titles into one text.

4. Embed

Step 9. Run the text through a small local model to get a vector.

Order of work

Credentials→ All subscriptions→ Channel details (batches of 50)→ Delete unsubscribed→ For each channel: uploads, save, commit→ Compare profiles→ Embed changed only→ Save vectors, commit

Everything before the embedding is a loop of small, independent units of work. Each channel is committed on its own, so a failure on one channel can't undo the others. The model runs once, in a single batch, at the end.

Step by step

The code for each step lives in src/bys/. Each card shows the function, what goes in and out, and what happens when it fails.

1

Load credentials

YouTube API
Code
auth.load_credentials
Input
~/.bys/token.json, written by bys login
Output
Google credentials that can call the API
Cost
No API units

Reads the saved token. If the access token has expired, it uses the refresh token to get a new one and saves the file again. The sync then uses this login without asking you anything.

Why

You log in once. Sync can run unattended, for example from cron.

If it fails

No token or an invalid one: sync stops with “Run bys login again.” Nothing is written.

2

List subscriptions

YouTube API
Code
youtube.list_subscribed_channel_ids
Call
subscriptions.list(part=snippet, mine=true, maxResults=50), repeated while there is a nextPageToken
Output
A list of channel IDs, such as ["UCczJ…", "UCabc…"]
Cost
1 unit per page, so 1 unit per 50 subscriptions

The API returns subscriptions 50 at a time. The helper _paginate keeps asking for the next page until the token is gone. The result is just IDs; the names come later.

Why

This list is the source of truth for what you follow. Everything else is derived from it.

If it fails

The whole sync stops. Without this list there is nothing to do, so this is the only network call that is fatal.

3

Fetch channel details

YouTube API
Code
youtube.fetch_channels
Call
channels.list(part=snippet,contentDetails, id=…50 IDs…)
Output
A Channel per ID: id, title, description, uploads_playlist_id, plus a list of Failures
Cost
1 unit per call, 50 channels per call

The IDs from step 2 are split into batches of 50. Each batch gets one call that returns the channel name, description, and the ID of its uploads playlist. The uploads playlist is the key to step 5: it's a YouTube playlist that holds every public video of that channel, newest first.

Why batches

One call for 50 channels instead of 50 calls. That keeps the quota use low.

If it fails

  • A batch errors: all 50 IDs in it are logged as failures, the next batch runs.
  • An ID is missing from the response (deleted or terminated channel): logged as “not returned by the YouTube API”.

4

Drop unsubscribed channels

SQLite
Code
db.remove_unsubscribed
SQL
DELETE FROM channels WHERE id NOT IN (…subscribed IDs…)
Cost
No API units

Anything in the local database that is no longer in your subscription list is deleted. Because of the foreign keys (see the schema), the matching rows in videos and embeddings are deleted too.

Subtle point. The list used here is the IDs from step 2, not the channels that step 3 managed to fetch. If step 3 failed for a channel, the channel is still in your subscriptions, so it is not deleted. Otherwise a temporary API error would wipe good data.

5

Fetch recent uploads, per channel

YouTube API
Code
youtube.fetch_recent_videos
Call
playlistItems.list(part=snippet,contentDetails, playlistId=UU…, maxResults=5)
Output
Up to 5 Videos: id, title, description, published_at
Cost
1 unit per channel. This is the biggest cost: 500 channels is 500 units.

For each channel, the code calls its uploads playlist and asks for the last 5 items. Videos titled “Deleted video” or “Private video” are removed. A channel without public uploads has no playlist, so the API returns 404; that is treated as “no videos”, not as an error.

Why only 5

Enough to describe what a channel covers now. More videos would mean more units and more text to embed, with diminishing returns.

If it fails

  • 404 on the playlist: channel saved with no videos. Not a failure.
  • Any other error (for example 403): this channel is logged and skipped.

6

Save each channel and its videos

SQLite
Code
db.save_channel, called from sync.sync_channels
SQL
INSERT … ON CONFLICT(id) DO UPDATE for the channel, DELETE the old videos, then INSERT the new ones
Commit
After every channel

The channel row is inserted or updated. Its old videos are deleted and the five fresh ones are inserted. Then the transaction is committed. The videos table only ever holds the last 5 per channel, because the delete happens on every sync.

Why commit per channel

If the sync crashes at channel 300, channels 1 to 299 are already saved. Re-running picks up the rest.

If it fails

The loop calls rollback(), which undoes only this channel's changes, logs the failure, and moves to the next channel.

7

Build the profile text

Profile
Code
profiles.build_profile
Input
One Channel and its Videos
Output
One string, at most 1500 characters
Cost
Local only

This is where a channel becomes text the model can read. The parts are added in this order: the channel name, the channel description, all recent titles, and then short snippets of each video description. URLs are removed and whitespace is collapsed. If the whole text is too long, the end is cut, so the snippets go first and the titles are kept.

The profile is what gets compared and what gets embedded. There is no other copy of the channel's meaning in the system.

A worked example, with real output, is in the worked example. The rules are in profile rules.

8

Detect changes

SQLite
Code
db.stored_profiles, compared in sync.sync
Read
SELECT channel_id, profile FROM embeddings
Output
The list of pending channels: new profile text differs from the stored one, or no stored profile
Cost
No API units, no model

Each profile from step 7 is compared with the profile stored at the last embedding. If they are the same, the channel keeps its vector. Only the different ones go to the model. This is what keeps a daily sync fast: most channels don't change from one day to the next.

← Build profileNext: embed →
9

Embed the changed profiles

Model
Code
embed.Embedder.embed_documents
Model
BAAI/bge-small-en-v1.5, run locally with fastembed (ONNX, no PyTorch)
Output
One vector per pending profile: 384 numbers, length 1
Cost
Local CPU time, no API cost

The pending profiles go to the model in one batch. The model turns each text into a list of 384 numbers that place it in “meaning space”: texts about similar things get vectors that point in similar directions. The vectors are normalized to length 1, so a dot product gives a similarity score between −1 and 1.

First run

The model is downloaded once, about 130 MB, and cached. Later runs start in seconds.

If it fails

The model is not inside the per-channel loop, so an error here stops the sync. The profile and channel data from earlier steps have already been committed and stay in the database.

SQLite
Code
db.save_embedding, then sync.sync returns a SyncResult
SQL
INSERT … ON CONFLICT(channel_id) DO UPDATE; the vector is stored as 384 float32 values in a BLOB (1536 bytes)
Output
A SyncResult: channels synced, channels re-embedded, and the list of failures

Each vector is saved next to the profile text it came from, plus the model name. Storing the profile is what makes step 8 work on the next run. The final commit makes all changes visible at once. The CLI then prints the summary and appends any failures to sync-failures.log.

YouTube API calls

Only three endpoints are used, all read-only. The quota numbers come from the Google documentation.

CallUsed inUnits per callItems per callCalls for 500 subscriptionsUnits
subscriptions.listStep 21501010
channels.listStep 3150 channel IDs1010
playlistItems.listStep 515 videos500500
Total520520
The default daily quota is 10,000 units, so a full sync uses about 5%. Sync never calls search.list, which is the expensive endpoint with its own small daily limit.

Calls are made one after another, not in parallel. That is slower, but it keeps the request rate predictable and makes the log easy to read in order.

Database schema

One SQLite file, ~/.bys/bys.db, with three tables. Lines show the foreign keys.

The SQL behind it

From src/bys/db.py. Read it as the source of truth.

CREATE TABLE IF NOT EXISTS channels (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    uploads_playlist_id TEXT,
    synced_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS videos (
    id TEXT PRIMARY KEY,
    channel_id TEXT NOT NULL REFERENCES channels(id) ON DELETE CASCADE,
    title TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    published_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS videos_channel_id ON videos(channel_id);
CREATE TABLE IF NOT EXISTS embeddings (
    channel_id TEXT PRIMARY KEY REFERENCES channels(id) ON DELETE CASCADE,
    profile TEXT NOT NULL,
    model TEXT NOT NULL,
    vector BLOB NOT NULL
);

What is not stored

  • Subscriptions as their own table. The channels table is the subscription list. Each row exists because you subscribe to it; step 4 removes the rest.
  • Full video history. Only the last 5 per channel are kept. Older rows are removed by step 6.
  • Transcripts or video files. Only titles and descriptions.
  • Your Google token. That lives in ~/.bys/token.json, outside the database.

The synced_at column records when a channel was last fetched. model records which model made each vector, so you can tell whether a re-embed is needed after switching models.

The query “the guys who make videos about golang” is embedded the same way, and its vector is compared with every stored vector. Gopher Academy should score highest. That part is covered by bys search, not by sync, but it depends on the vectors this page describes.

Re-runs: what gets re-embedded?

Sync can run again at any time. Only what changed is re-embedded.

SituationWhat sync doesModel called?
First ever syncEvery channel is new: all profiles are pending.Yes, for all
Nothing changed since yesterdayProfiles match the stored ones. Nothing is pending.No
One channel uploaded a videoIts last-5 list changes, so its profile changes.Yes, for that channel
A video description was editedThe description snippet is part of the profile, so the profile changes.Yes, for that channel

You subscribed to a new channelNew row, new profile, nothing stored yet.Yes, for that channel

The decision for each channel

Build profile→ Stored profile exists?→ No→ Embed
Stored profile exists?→ Yes, same text→ Keep vector
Stored profile exists?→ Yes, different text→ Embed

Failure handling

Failures are handled at the smallest level that makes sense. A problem with one channel never stops the others.

LevelExampleWhat happens
Global, fatalNo token, bad token, subscriptions.list fails, model fails to loadSync stops with an error. Nothing after that step runs.
Batchchannels.list returns an error for 50 IDsThose 50 IDs are logged. The next batch runs.
Channel403 on a channel's uploads playlist, or a database error while saving itThe channel's changes are rolled back, the failure is logged, and the next channel runs.
Not a failure404 on the uploads playlist (no public uploads)The channel is saved with no videos and its profile is built from the description.
MissingAn ID is not returned by channels.listLogged as “not returned by the YouTube API”.

Where the failures go

  • Console: a failed: line right after the channel's progress line, and a summary at the end.
  • Log file: ~/.bys/sync-failures.log, appended on every run, one line per failure:
2026-11-25T09:00:12+00:00	Karting Pro (UCxxxx)	HTTP 403: forbidden

The log is append-only, so you can see the history of a channel that keeps failing. A channel that appears in every run is a good candidate for a closer look.

The sync exits with status 0 even when some channels failed. A partial sync is still a success from the database's point of view. Check the summary, or the log, to see what was skipped.

Profile rules

These limits are in src/bys/profiles.py. They keep the profile inside the model's input size.

RuleValueWhy
Remove URLsany http(s):// or www. linkLinks are noise to the model and can be very long.
Collapse whitespaceruns of spaces, tabs and newlines → one spaceKeeps the text compact.
Channel description cap500 charactersEnough to say what the channel is about.
Video description snippet cap150 characters eachThe start of a description usually says what the video is about.
Total profile cap1500 charactersThe model reads at most about 512 tokens. Anything after that is ignored anyway.
Truncation pointat a word boundary, with ...Avoids cutting a word in half.
Ordername → channel description → titles → snippetsTitles are the most specific signal, so they come before the snippets, which get cut first.
Titles come before the snippets, but after the channel description. If the channel description takes the full 500 characters, the titles still fit inside the 1500 total. The rule is about what survives truncation, not what is first in the text.

Glossary

SubscriptionYour follow of a channel. Stored as the channel's row in channels.
Uploads playlistA YouTube playlist that lists every public video of a channel, newest first. Its ID starts with UU.
Quota unitYouTube's budget unit. Most read calls cost 1; the default daily budget is 10,000.
PaginationThe API returns results in pages. Use the nextPageToken to get the next one.
ProfileThe plain text that describes a channel, built in step 7.
EmbeddingA list of numbers that represents the meaning of a text. Similar texts get similar numbers.
VectorThe same as an embedding here: 384 numbers, stored as a BLOB.
NormalizedScaled so the vector has length 1. Then the dot product of two vectors is their cosine similarity.
UpsertInsert the row, or update it if the key already exists. The SQL ON CONFLICT … DO UPDATE.
Commit / rollbackCommit makes a group of changes permanent. Rollback throws away the uncommitted ones.
Foreign key, cascadeA column that points at another table's key. ON DELETE CASCADE deletes the dependent rows automatically.
BatchSeveral IDs sent in one API call. The channel lookup uses batches of 50.
fastembedA Python library that runs embedding models with ONNX Runtime, without PyTorch.
